大模型处理输入时要进行大量计算。为了避免重复劳动，服务商会把一部分计算结果暂时保存起来，供后续请求复用，这就是缓存。当这次请求里有符合条件的输入、可以直接复用已保存的结果时，我们说它「缓存命中」，通常更快也更便宜；反过来，没有可复用的东西、需要重新计算时，就是「缓存未命中」，耗时更多，输入费用也更高。要注意的是，大模型的提示词缓存保存的是计算过程中产生的中间状态，而不是问题的标准答案。

由此引出一个很自然的问题：既然「什么是人工智能」这样的问题已经被一百万人问过，为什么我再问一次，还不一定能命中缓存？原因在于，每次请求的完整输入可能完全不同——系统提示词不一样，对话历史不一样，工具定义不一样，输入的开头也不一样，再加上缓存本身会过期、当前请求也未必有权访问到相应的缓存。所以问题本身很热门，并不代表这次请求就一定命中。缓存看的是符合规则的输入前缀能否复用，而不是这个问题在全世界被问过多少次。

以 DeepSeek 官方 API 为例，它支持自动提示词缓存，核心机制是：当多个请求具有相同的输入前缀时，后续请求有机会复用已经缓存的计算结果。比如你第一次问「请用通俗易懂的中文解释技术概念。什么是 API？」，第二次问「请用通俗易懂的中文解释技术概念。什么是 CDN？」，前面的指令完全相同，后面的具体问题不同。只要公共前缀足够长、缓存仍然可用，第二次请求就可能命中前面那部分缓存，只需要为后半段的新内容付费计算。反过来说，即使两个问题一模一样，如果它们前面的系统提示词和上下文不同，也未必能命中。另外有几点需要留意：DeepSeek 的缓存按一定的 Token 单元处理；缓存不是永久保存的；命中也没有百分之百的保证；即使部分输入命中了缓存，模型仍然要根据当前请求生成属于你的答案。

讨论里最值得思考的问题是：为什么不把所有用户问过的热门问题都缓存起来？一种直观的设想是，既然很多人反复问相同的问题，服务商完全可以建一个全体用户共享的缓存，让后面的人都享受低价。这个方向有一定技术可行性，但要区分两种不同的机制。第一种是公共答案缓存，问题完全相同就直接返回以前保存的答案。它适合某些固定查询，但用在聊天场景有明显局限：用户的上下文、要求、语言、回答风格和所需信息的时效都可能不同，直接把旧答案搬过来，可能出错，也可能不合适。第二种是提示词计算缓存，保存的是模型处理相同输入前缀时产生的中间计算状态。它并不是把以前的答案拿给你，而是跳过重复计算的部分，然后继续生成当前请求所需要的回答。DeepSeek 的提示词缓存属于第二种思路。

缓存确实涉及商业利益。命中缓存时，服务商减少了重复计算，用户通常也享受更低的输入价格；未命中时，相应部分要重新计算，成本和收费都会更高。提高命中率，对服务商意味着更低的计算成本和更快的响应速度，所以他们有动力去做这件事，但同时也要权衡缓存的存储开销、访问速度、服务器调度、有效期以及用户之间的数据隔离。这里必须把两件事分开：一，未命中会导致用户支付更高的输入费用，这是计费规则决定的；二，未命中是不是服务商为了多收费而故意造成的，这需要额外证据。前一个问题看规则就能回答，后一个问题不能单凭一次未命中就下结论。

如果想确认自己有没有命中，用 DeepSeek 官方 API 的话，可以看返回结果里的 Token 用量统计：`prompt_tokens` 是输入 Token 总量，`prompt_cache_hit_tokens` 是命中缓存的输入 Token 数，`prompt_cache_miss_tokens` 是未命中的数量（具体字段以接口实际返回为准）。命中率可以用「缓存命中的 Token 数 ÷ 输入 Token 总数 × 100%」来算，比如输入共 5000 Token、其中 4000 命中，命中率就是 80%。如果用的是网页或手机 App 聊天，通常看不到这些字段。

这次讨论的结论可以归纳成四句话：别人问过很多遍，不代表你这次一定命中缓存；缓存命中取决于输入前缀及缓存是否可用，而不是问题有多热门；技术上可以通过公共前缀缓存复用不同用户请求中的相同计算，但这不等于存在一个全体共享的公共答案库；缓存规则会影响服务商的成本和用户的费用，但不能仅凭未命中就断定服务商故意多收费。最值得继续研究的问题是：既然公共前缀缓存能够减少重复计算，服务商还能通过哪些技术手段进一步提高命中率，让更多用户以更低的成本用上大模型？
